# Edu7 — الخطة المقترحة النهائية بعد إعادة تقييم تقرير الفجوات

**التاريخ:** 2026-09-14  
**النطاق:** إعادة تقييم ملف `docs/Autonomous Architecture, Lifecycle & Data Flow Gap Audit.md`، ثم تحديث الخطة بعد المراجعة التنفيذية الثانية التي أضافت: حماية جفاف بنك الأسئلة، دورة التصحيح اليدوي، واجهة المساعد الذكي، الاستيراد الجماعي للوزاري، التشخيص القبلي، الصمود أمام ضعف الاتصال، وتدفق مهام ولي الأمر الاستشارية. تشمل الخطة أيضًا إضافة **OpenAI API** بجانب **Gemini API** خلف منفذ AI موحد، وتحديثات المنتج الأخيرة: تخصصات المعلمين متعددة المواد، منع اختلاط الدروس والمواد، الاستمرار من آخر نقطة، خيارات ما بعد اختبار الدرس، وتحسين إدارة الكتب والمحتوى.

---

## 0. الحكم النهائي المختصر

التقرير الشامل صحيح في جوهره: **Edu7 يملك قلبًا خلفيًا ناضجًا للتعلم التكيفي، لكن واجهات المستخدم لا تغلق كل حلقات التشغيل**. لكن التقرير لا يُقبل كخطة تنفيذية نهائية بصيغته الحالية إلا بعد تعديل النقاط الآتية:

1. **إضافة إصلاحات سلامة قبل بناء الميزات**: بوابة رف مواد المعلم، وفجوة قراءة بيانات متعلم عبر مدرسة أخرى، ومعالجة فشل محاولات الاختبار عند ضعف الاتصال.
2. **تعديل حكم “الشعبة/الفصل”**: لا يُنفّذ `ClassSection/TeacherAssignment` فورًا لأنه يصطدم بقرار موثق سابقًا أن “الفصل استعلام فوق التسجيلات”. يُقبل فقط كقرار منتج مشروط عندما توجد مدارس فيها أكثر من معلم لنفس الصف/المادة أو شعب فعلية مستقلة.
3. **إضافة فجوة `GradeSubject`**: مصفوفة الصف × المادة موجودة لكنها غير منفذة عند إنشاء/تبني الكتب.
4. **إضافة محور بنك الأسئلة الجديد**: نوع السؤال موجود في الدومين، لكن لا واجهة له؛ ومصدر السؤال يحتاج توسيعًا ليشمل `MINISTERIAL` مع نموذج مصدر وزاري منظم، لا مجرد نص حر.
5. **إضافة حارس نقص الأسئلة**: لا يكفي تقرير readiness؛ يجب ألا يصل الطالب إلى تجربة مكسورة عندما لا توجد أسئلة منشورة لمفهوم أو درس.
6. **إضافة دورة المقال والتصحيح اليدوي**: وجود `QuestionType.ESSAY` و `REQUIRES_MANUAL_REVIEW` لا يكفي بلا طابور تصحيح، ورصد درجة، وإعادة حساب إتقان.
7. **إحياء واجهة المساعد الذكي**: API موجود، لكنه يتطلب مكونًا داخل الدرس، مع بقاء الإجابة grounded ومحدودة بالكوتا.
8. **إضافة OpenAI بجانب Gemini**: لا يجب ربط Edu7 بمزوّد واحد. المزودان يعملان خلف `AiProvider` واحد، مع fallback حتمي إلى المزود deterministic عند غياب المفاتيح أو فشل الشبكة.
9. **تخصص المعلم يصبح علاقة منظمة بالمواد**: يبقى النص الحر ملاحظة legacy فقط، بينما المصدر التشغيلي لتأليف/تكليف المعلم هو قائمة مواد مرتبطة قابلة للتعدد.
10. **مسار الدرس يجب أن يكون deterministic**: عرض الدرس، مواده، اختباراته، ومفهومه يجب أن يفلتر دائمًا على `lessonKey`/`conceptKey` الحالي وألا يعيد استخدام موارد درس آخر.
11. **إغلاق تجربة ما بعد اختبار الدرس**: بعد الإغلاق يرى الطالب خيار العودة للرئيسية أو متابعة الدرس التالي؛ وعند آخر درس يرى تنبيه انتهاء كل الدروس قبل العودة للرئيسية.
12. **الاستمرار من آخر نقطة**: لوحة الطالب ومسار التعلم يجب أن يقترحا آخر درس/مفهوم/نشاط غير مكتمل بدل البدء من أول الكتاب دائمًا.
13. **إدارة الكتب والمحتوى ليست جداول فقط**: تحتاج مؤشرات صحة، روابط عمل مباشرة، عرضًا هرميًا للوحدة/الدرس/المواد، وفلاتر تسهل التشغيل اليومي.

## 1. إعادة تقييم التقرير والتقييم التنفيذي الثاني

| البند | قرار التقييم | السبب |
|---|---|---|
| كسر زر `NextStepCard` وتحويله دائمًا إلى `/path` | **مقبول** | الخلل فعلي: قرار المحرك التكيفي يظهر في البطاقة، لكن زر البدء لا ينفذه. |
| غياب واجهات `instruction` | **مقبول** | دورة الخطط/الالتزامات موجودة خلفيًا، ولا يوجد استهلاك واجهة كافٍ لها. |
| غياب رادار التدخلات العلاجية | **مقبول** | `RemediationEpisode` و tracker موجودان، لكن لا شاشة معلم/طالب تغلق الحلقة. |
| غياب واجهة المساعد الذكي | **مقبول ومرفوع الأولوية** | `POST /tutoring/ask` موجود، لكن بلا Drawer داخل `LessonPage`. يجب ألا يتحول إلى Chat عام خارج سياق الدرس. |
| `ClassSection/TeacherAssignment` كتصحيح فوري | **غير مقبول بصيغته الحتمية** | يوجد قرار موثق بأن الفصل Query فوق Enrollment. يُقبل فقط عند تحقق trigger منتجي: شعب حقيقية أو أكثر من معلم لنفس الصف/المادة. |
| “كل معلم يرى كامل الصف” | **مقبول كحد معروف** | ليس خطأ قاتلًا إلا إذا كان المنتج يستهدف مدارس ذات شعب/توزيع مواد تفصيلي. |
| نشر كتاب دون تغطية أسئلة كافية | **مقبول كفجوة حرجة** | readiness الحالي لا يمنع عمليًا تجربة `assessment.empty_item_pool`. يجب إضافة preflight/fallback لا مجرد تقرير. |
| Legacy PDF/Excel ingestion | **مقبول لكن بعد تثبيت نموذج البنك** | الاستيراد مفيد، لكن قبل ذلك يجب تثبيت نموذج السؤال، المصدر، الربط بالمفهوم، وقواعد النشر. |
| لوحة الصدارة | **مقبول كأولوية منخفضة** | موجودة خلفيًا، لكنها ليست سدًا لحلقة تعليمية حرجة. |
| نقص الأسئلة في CAT | **مقبول كـ P0/P1** | تقنيًا يرجع `Err(precondition)` لا ينهار الـ process، لكنه يسبب انهيار تجربة الطالب إن تُرك للواجهة كخطأ عام. |
| المقال والتصحيح اليدوي | **مقبول كفجوة بنيوية** | `ESSAY` موجود، لكن لا دورة معلم تكمل النتيجة وتعيد بث evidence/mastery. |
| التشخيص القبلي | **مقبول** | وجود `AttemptKind.DIAGNOSTIC` دون onboarding placement يجعل الطالب يبدأ من الدرس الأول حتى لو كان متقدمًا. |
| الاتصال الضعيف | **مقبول كأولوية سياقية** | البيئة المستهدفة تجعل حفظ المحاولة محليًا مطلب سلامة لا تحسينًا ثانويًا. |
| مهام ولي الأمر الاستشارية | **مقبول بضبط UI** | الـ backend يميز advisory، لكن واجهة الطالب/ولي الأمر يجب أن تعرضه بوضوح دون أثر أكاديمي. |

## 1.1 تقييم التصميم التعليمي وتجربة الطالب بعد المراجعة الأخيرة

التقييم التصميمي الأخير لا يغيّر قواعد الدومين، لكنه يصحّح طريقة تقديمها للطالب والمؤلف. الخلاصة: **القلب التكيفي لا يكفي إذا بقيت الواجهات التعليمية قوائم رمادية أو صفحات درس فقيرة**. لذلك تُربط إصلاحات المرحلة 7 بتصميم الواجهات التعليمية نفسها، لا بإدارة المحتوى فقط.

| الواجهة | المشكلة التصميمية | التصحيح المطلوب |
|---|---|---|
| `subjects.tsx` | المواد والكتب ظهرت كروابط مسطحة لا تحمل هوية المادة ولا تشجع الاستمرار. | هوية مادة واضحة بأيقونات/ألوان، بطاقات كتب ذات progress ظاهر، وزر **Quick Resume** يفتح آخر نقطة ذات معنى لكل كتاب. |
| `learning-path.tsx` | مسار التعلم كان قائمة تقنية يصعب منها فهم أين الطالب ولماذا قُفل درس. | تحويله إلى visual trail/timeline، accordion ذكي للوحدات، إبراز الدرس الحالي وفتح وحدته تلقائيًا، وشرح سبب القفل بأسماء prerequisites. |
| `lesson.tsx` | الدرس كان فقرة قراءة ثم روابط، فلا يشعر الطالب برحلة تعلم. | درس منظم غني: مراحل **Absorb / Reinforce / Verify**، reading blocks، sticky prev/next navigation، وحفظ `textbook` في breadcrumb/path. |
| `dashboard.tsx` | مؤشرات كثيرة بلا أفعال واضحة، ونبرة بصرية أقل تحفيزًا من لوحة junior. | metrics تفاعلية تقود إلى مراجعة/معالجة، ترتيب بصري موحد، إبراز due work/streak/weekly goal، وتوحيد نبرة التحفيز مع junior دون تبسيط مفرط. |
| `junior-dashboard.tsx` | فيه عناصر تحفيزية ناجحة لكنها منفصلة عن تجربة الطالب الأكبر. | استخدام لغته التحفيزية كمصدر نمط للـ senior dashboard؛ والـ continue learning يفتح الدرس الحالي مباشرة عند توفره. |

### قواعد تنفيذ التصميم

1. **الهوية البصرية ليست زخرفة**: لون/أيقونة المادة يجب أن يساعدا الطالب على التمييز بين العلوم/الرياضيات/العربية بسرعة.
2. **الاستمرار أهم من الاستكشاف**: أي شاشة رئيسية أو مادة يجب أن تعرض آخر نقطة تعلم قابلة للاستكمال قبل روابط التصفح العامة.
3. **القفل يجب أن يشرح نفسه**: لا يكفي زر disabled؛ يجب ذكر المتطلبات السابقة التي تمنع فتح الدرس/المفهوم.
4. **اتجاه RTL/mobile**: كل أزرار touch الأساسية لا تقل عن 44px، والأسهم تتبع اتجاه اللغة؛ في العربية السهم للدرس التالي بصريًا يكون مناسبًا لاتجاه RTL.
5. **الأداء**: مسارات الكتب الكبيرة تحتاج virtualization أو deferred rendering عند نمو عدد الدروس/المفاهيم، مع إبقاء accordion للوحدة الحالية فقط مفتوحًا افتراضيًا.
6. **مفاتيح الاستعلام**: يجب توحيد مفاتيح التعلم مثل `queryKeys.learning.journey` و`queryKeys.learning.nextStep` حتى لا تتسرب حالة كتاب/درس سابق إلى شاشة حالية.

**معيار القبول التصميمي:** يستطيع الطالب من لوحة القيادة الوصول إلى آخر درس، فهم مكانه في المسار، معرفة سبب القفل، قراءة درس منظم، ثم العودة للرئيسية أو الانتقال للدرس التالي بعد التقويم دون أن يرى موارد درس آخر أو يفقد سياق الكتاب.

## 2. القاعدة المعمارية الحاكمة لبنك الأسئلة

> السؤال له **نوع** يحدد كيف يُصحح، وله **مصدر** يحدد من أين جاء، وله **روابط مفاهيم** تحدد ماذا يقيس.  
> لا يجوز لأي واحد من هذه الثلاثة أن يحل محل الآخر.

| البعد | المقصود | أمثلة | أثره في النظام |
|---|---|---|---|
| `QuestionType` | طريقة الإدخال والتصحيح | `MCQ_SINGLE`, `TRUE_FALSE`, `NUMERIC`, `ESSAY` | يحدد editor/evaluator/manual-review. |
| `QuestionOrigin` | مصدر السؤال وسلسلة الإثبات | `TEXTBOOK`, `TEACHER`, `MINISTERIAL`, `AI`, `UNKNOWN` | يحدد provenance والفلترة والملكية. |
| `QuestionConcept` | ماذا يقيس السؤال | مفهوم رئيسي + مفاهيم ثانوية | يحدد أثر الإجابة على mastery و BKT/IRT. |
| `Attempt/Exam policy` | ما المصادر المسموحة في محاولة معينة | كتاب فقط، وزاري فقط، معلم + رسمي | يحدد اختيار الأسئلة لا قواعد الإتقان نفسها. |

### 2.1 التعريف النهائي للمصادر

| المصدر | المعنى | الملكية | قابلية الاستخدام |
|---|---|---|---|
| `TEXTBOOK` | سؤال/تمرين مطبوع في الكتاب أو منقول منه | مؤلف/إدارة المحتوى | يظهر كتمارين كتاب، ويخضع لقفل الكتاب بعد النشر. |
| `TEACHER` | سؤال ألّفه معلم لدعم طلابه | المعلم/المدرسة | school/teacher scoped، ولا يلوث البنك الرسمي دون مراجعة. |
| `MINISTERIAL` | سؤال من نماذج امتحانات وزارية رسمية أو أعوام سابقة | مصدر وزاري موثق | يستخدم للتدريب على نمط الامتحان، مع سنة/دور/صف/مادة/مصدر. |
| `AI` | سؤال مولّد آليًا | النظام/المؤلف الذي راجعه | لا يصبح منشورًا قبل مراجعة وتصحيح وقياس جودة. |
| `UNKNOWN` | سؤال تاريخي مجهول المصدر | غير معروف | يسمح بحفظه لكن يظل بحاجة لتدقيق provenance. |

### 2.2 الحد الأدنى المقبول للبيانات

1. إضافة قيمة إلى enum:

```prisma
enum QuestionOrigin {
  TEXTBOOK
  TEACHER
  MINISTERIAL
  AI
  UNKNOWN
}
```

2. إبقاء `sourceRef` كمرجع وصفي مرحلي مثل: `MOE-YE-2024-G09-MATH-R1-Q12`.
3. إضافة فلاتر البنك حسب:
   - `type`
   - `origin`
   - `textbookRole`
   - `grade`
   - `subject`
   - `lesson`
   - `concept`
   - `status`
   - `sourceDocument`

### 2.3 النموذج الأقوى للأسئلة الوزارية

إضافة كيان مصدر رسمي بدلاً من حشر كل شيء في `sourceRef`:

```prisma
model QuestionSourceDocument {
  id             String @id @default(uuid()) @db.Uuid
  key            String @unique
  origin         QuestionOrigin
  title          String
  countryCode    String?
  authorityName  String?
  academicYear   String?
  gradeId        String? @db.Uuid
  subjectId      String? @db.Uuid
  termId         String? @db.Uuid
  examSession    String?
  sourceUrl      String?
  fileHash       String?
  createdAt      DateTime @default(now())
}
```

ثم يرتبط السؤال اختياريًا بـ:

```prisma
sourceDocumentId String? @db.Uuid
sourceQuestionNo String?
sourcePage       Int?
```

**السبب:** السؤال الوزاري ليس مجرد “تمرين”؛ هو جزء من ورقة امتحانية لها سنة/دور/صف/مادة ومصدر إثبات.

### 2.4 واجهة بنك الأسئلة المطلوبة

1. **قائمة بنك الأسئلة**:
   - بحث نصي.
   - فلتر نوع السؤال.
   - فلتر المصدر: كتاب / معلم / وزاري / AI / مجهول.
   - فلتر الحالة: Draft / In review / Published / Archived.
   - فلتر الصف/المادة/الكتاب/الدرس/المفهوم.
   - شارات واضحة: `نوع السؤال` + `المصدر` + `حالة النشر` + `مرتبط بمفهوم؟`.

2. **محرر السؤال الديناميكي**:
   - `MCQ_SINGLE`: خيارات + إجابة واحدة.
   - `MCQ_MULTI`: خيارات + إجابات متعددة.
   - `TRUE_FALSE`: خياران فقط.
   - `NUMERIC`: قيمة/مدى/سماحية.
   - `SHORT_TEXT/FILL_BLANK`: إجابات نصية مقبولة.
   - `MATCHING`: أزواج.
   - `ORDERING`: ترتيب.
   - `ESSAY`: prompt + rubric + درجة قصوى + manual-review lifecycle.

3. **قسم المصدر**:
   - إذا `TEXTBOOK`: إظهار `TextbookQuestionRole` = Exercise / Self-test / Review / Other.
   - إذا `TEACHER`: إظهار مالك السؤال ونطاقه: خاص بالمعلم / المدرسة / مرشح للمراجعة.
   - إذا `MINISTERIAL`: اختيار ورقة وزارية أو إدخال بياناتها: سنة، دور، صف، مادة، رقم السؤال، الصفحة/الرابط.

4. **ربط المفاهيم**:
   - استخدام `web/src/education/authoring/question-link-modal.tsx` بدل إبقائها بلا مستهلك.
   - لا ينشر السؤال قبل ربطه بمفهوم واحد على الأقل وتحديد primary concept.

## 3. الثغرات الحرجة المضافة بعد المراجعة الثانية

### 3.1 جفاف بنك الأسئلة في CAT / Empty Pool Guard

**الملاحظة:** `RunAdaptiveExamUseCase` يرجع `assessment.empty_item_pool` عندما لا توجد أسئلة نشطة لنطاق المفهوم. هذا صحيح كـ domain error، لكنه غير كافٍ كتجربة منتج.

**المطلوب:**

1. Endpoint/قراءة جاهزية محاولة قبل إظهار زر الاختبار:
   - `GET /assessment/availability?conceptKey=&lessonKey=&kind=` أو دمجها في lesson/next-step view.
2. إخفاء أو تعطيل زر الاختبار عندما لا توجد أسئلة منشورة، مع رسالة تعليمية بديلة.
3. fallback تربوي مضبوط:
   - مراجعة/بطاقات بدلاً من اختبار.
   - أو تمرين من المفهوم الأب فقط إذا كانت السياسة تسمح بذلك وتُسجل في `attempt.policy`.
   - أو fixed-form non-adaptive إذا كانت هناك أسئلة كافية للتدريب لكن لا تكفي CAT.
4. telemetry/report:
   - تسجيل نقص pool حسب grade/subject/lesson/concept/origin/type لإغلاق الفجوة من لوحة item-health.

**قاعدة مهمة:** لا نزوّر التكيف. إذا استخدمنا fallback غير تكيفي يجب وسم المحاولة صراحة، ولا نحسبه كـ CAT كامل.

### 3.2 دورة التصحيح اليدوي للمقالي

**الملاحظة:** وجود `QuestionType.ESSAY` و `REQUIRES_MANUAL_REVIEW` يمنع التصحيح الآلي الخاطئ، لكنه لا يكمل رحلة الطالب والمعلم.

**المطلوب:**

1. إنشاء طابور تصحيح للمعلم/المؤلف:
   - `/teacher/grading` أو `/author/grading` حسب ملكية السؤال/التكليف.
2. عرض إجابة الطالب، السؤال، rubric، الدرجة القصوى، ومحاولة الطالب.
3. إدخال الدرجة والتعليق:
   - `scoreEarned`
   - `feedback`
   - `gradedByUserId`
   - `gradedAt`
4. عند اعتماد التصحيح:
   - تحديث attempt item evaluation من `REQUIRES_MANUAL_REVIEW` إلى graded result.
   - إنشاء/تحديث `MasteryEvidence` للمفاهيم المرتبطة.
   - طلب recompute للـ mastery/BKT.
5. إشعار الطالب بأن نتيجة سؤال/محاولة تغيرت بعد التصحيح.

**قاعدة مهمة:** يمكن استعمال AI كمساعد اقتراح rubric/feedback، لكن القرار النهائي للدرجة في المقال يجب أن يبقى manual أو explicit human-approved في النسخة الأولى.

### 3.3 المساعد الذكي داخل الدرس + OpenAI/Gemini

**الملاحظة:** backend tutoring موجود، لكن لا توجد واجهة داخل الدرس. كذلك الاعتماد على Gemini فقط يجعل التشغيل مرتبطًا بمزوّد واحد.

**المطلوب:**

1. إضافة `TutorDrawer` داخل `LessonPage`:
   - يرسل `lessonKey`, `textbookKey`, وربما `conceptKey` إلى `POST /tutoring/ask`.
   - يعرض الإجابة مع citations.
   - يعرض حالة refusal عندما لا توجد grounding كافية.
   - يعرض quota remaining/reset.
2. منع الاستخدام كـ chatbot عام:
   - لا سؤال بلا lesson/textbook/concept context إلا لسيناريو مصرح.
   - لا إجابة بلا grounding كافٍ.
3. إضافة OpenAI كمزوّد ثانٍ خلف نفس `AiProvider`:
   - `GeminiProvider`
   - `OpenAiProvider`
   - `DeterministicProvider`
4. ترتيب مزودين قابل للضبط:
   - `AI_PROVIDER_ORDER=gemini,openai,deterministic`
   - أو `openai,gemini,deterministic` حسب بيئة التشغيل.
5. تسجيل provider/model/tokens/latency في `AiInteraction` كما هو التصميم الحالي.

**قاعدة مهمة:** OpenAI و Gemini ليسا دومين. هما adapters في `src/infrastructure/ai/*`، ولا يجب أن تتسرب أسماء الموديلات إلى `contexts/tutoring`.

### 3.4 الاستيراد الجماعي للنماذج الوزارية

**الملاحظة:** إدخال 50-100 سؤال لكل ورقة وزارية سؤالًا بسؤال غير قابل للتشغيل.

**المطلوب:**

1. أداة Import Wizard للنموذج الوزاري:
   - بيانات الوثيقة مرة واحدة: البلد/الجهة/السنة/الصف/المادة/الدور.
   - لصق Markdown/JSON/CSV أو رفع ملف PDF/Excel لاحقًا.
2. Parser ينتج قائمة أسئلة draft:
   - نوع السؤال.
   - الخيارات/الإجابة.
   - رقم السؤال.
   - الصفحة.
   - المصدر الوزاري.
3. شاشة preview قبل الحفظ:
   - أخطاء parsing.
   - أسئلة ناقصة answer key.
   - أسئلة بلا concept link.
   - احتمالات التكرار.
4. حفظ جماعي كـ `origin=MINISTERIAL` مع `sourceDocumentId`.
5. ربط جماعي بالمفاهيم أو فتح workflow ربط متتالٍ.

### 3.5 التشخيص القبلي / Diagnostic Placement Loop

**الملاحظة:** وجود `AttemptKind.DIAGNOSTIC` دون تجربة placement يجعل المسار يبدأ دائمًا من أول الكتاب.

**المطلوب:**

1. عند تسجيل الطالب أو بداية عام/مادة:
   - عرض تشخيص قبلي قصير حسب الصف/المادة/الوحدة.
2. اختيار أسئلة منشورة كافية وموثوقة، ويفضل تغطية مفاهيم prerequisite الأساسية.
3. نتائج التشخيص:
   - لا “تلغي” المنهج.
   - لكنها تضبط نقطة البداية، توصيات next-step، وربما تفتح دروسًا يتضح إتقان متطلباتها.
4. تمييز evidence التشخيصية:
   - `AttemptKind.DIAGNOSTIC`
   - وزن/سياسة منفصلة عن ممارسة يومية أو اختبار وزاري.
5. تقرير للمعلم: الطلاب الذين يحتاجون تأسيسًا قبل الوحدة.

### 3.6 الصمود أمام الاتصال الضعيف / Local Attempt Recovery

**الملاحظة:** الطالب قد يفقد إجابات محاولة طويلة بسبب انقطاع الاتصال.

**المطلوب:**

1. حفظ محلي مؤقت في الواجهة:
   - IndexedDB كخيار أول.
   - localStorage كاحتياط صغير فقط.
2. تخزين:
   - `attemptKey`
   - السؤال الحالي.
   - الإجابات draft.
   - timestamp/version.
3. إرسال idempotent للجوابات:
   - لا يكرر الدرجات إذا أعاد الطالب الإرسال بعد عودة الاتصال.
4. شاشة استعادة:
   - “وجدنا محاولة غير مرسلة؛ هل تريد استعادتها؟”
5. حماية الخصوصية:
   - عدم حفظ answer keys.
   - مسح buffer عند التسليم الناجح أو logout.

### 3.7 مهام ولي الأمر الاستشارية في واجهة الطالب

**الملاحظة:** backend يميز academic/advisory في due-work، لكن يجب أن يظهر ذلك بوضوح في المنتج.

**المطلوب:**

1. بطاقة منفصلة في لوحة الطالب:
   - “توصيات من ولي الأمر”.
   - لون/أيقونة advisory لا تشبه الواجب الرسمي.
2. لا تدخل في:
   - mastery.
   - lesson unlock.
   - completion الرسمي.
   - تنبيهات التأخر الأكاديمي.
3. في بوابة ولي الأمر:
   - إنشاء/إلغاء task advisory.
   - رؤية الحالة بدون صلاحية override أكاديمية.
4. في `Due Work`:
   - عرض `academic` و `advisory` في قائمتين لا قائمة مختلطة.

### 3.8 تخصصات المعلمين متعددة المواد

**الملاحظة:** حقل تخصص نصي واحد لا يكفي لأن المعلم قد يدرّس أكثر من مادة، ولا يصلح النص الحر كمصدر صلاحيات أو فلاتر تكليف.

**المطلوب:**

1. نموذج ربط `EducatorSubjectSpecialty` بين ملف المعلم و`Subject`.
2. دعم إنشاء/تحديث المعلم بقائمة `subjectKeys`، مع إبقاء `specialty` كملاحظة legacy اختيارية.
3. عرض مواد التخصص في صفحة المعلمين وتفاصيل المستخدم بأسماء المواد لا كمفاتيح خام.
4. استخدام هذه العلاقة لاحقًا في فلترة أسئلة/تكليفات المعلم دون خلق `TeacherAssignment` كامل قبل تحقق شروط الشعب.

### 3.9 سلامة عرض الدروس واستكمال المسار

**الملاحظة:** أي خلط بين مواد درس وآخر أو اختبار درس وآخر يكسر الثقة في المسار التكيفي حتى لو كان backend صحيحًا.

**المطلوب:**

1. ترتيب الوحدات والدروس حسب `order` وعدم الاعتماد على ترتيب وصول API.
2. كل استعلام موارد/اختبارات/مفاهيم داخل `LessonPage` يجب أن يستخدم `lessonKey` الحالي فقط.
3. بعد إنهاء اختبار الدرس:
   - إظهار زر العودة للرئيسية.
   - إظهار زر الانتقال للدرس التالي إذا وجد.
   - إذا لم يوجد درس تالٍ، إظهار رسالة انتهاء جميع الدروس ثم تسهيل العودة للرئيسية.
4. “استمر من آخر نقطة” في لوحة الطالب يجب أن يفضّل آخر درس/مفهوم غير مكتمل أو آخر توصية next-step، لا أول درس في الكتاب.
5. حفظ آخر نقطة يجب أن يستند إلى evidence/progress الموجودة لا إلى ذاكرة واجهة مؤقتة فقط.

### 3.10 تحسين واجهة إدارة الكتب وإدارة المحتوى

**الملاحظة:** شاشة الكتب والمحتوى إذا بقيت قائمة مسطحة فقيرة لن تساعد المؤلف/الإدارة على تشغيل النشر والجاهزية.

**المطلوب:**

1. إدارة الكتب:
   - مؤشرات عددية: إجمالي النتائج، المنشور، المتبنّى، وأسئلة الصفحة/الكتاب.
   - فلاتر أوضح مع مسح سريع.
   - روابط مباشرة إلى إدارة محتوى الكتاب وتبنّياته ودورة النشر.
2. إدارة المحتوى:
   - عرض هرمي: كتاب ➜ وحدات ➜ دروس ➜ مواد/مفاهيم.
   - Drawer مواد الدرس مع نوع المادة والحالة والرابط.
   - فحص جاهزية بصري: درس بلا مواد، مفهوم بلا أسئلة، سؤال بلا concept link.
   - نوايا عمل واضحة: معاينة الدرس، إدارة المواد، ربط الأسئلة، مراجعة الجاهزية.
3. عدم جعل الواجهة مجرد `DataTable` عندما تكون العلاقة الهرمية هي المعنى الأساسي للمحتوى.

## 4. معمارية الذكاء الاصطناعي بعد إضافة OpenAI

### 4.1 الوضع المطلوب

يجب أن تكون سلسلة المزودين:

```txt
Tutor UI
  -> POST /tutoring/ask
    -> AskTutorUseCase
      -> quota
      -> ContextRetriever
      -> GroundingPolicy
      -> AiProvider chain
           1. GeminiProvider أو OpenAiProvider حسب AI_PROVIDER_ORDER
           2. المزود الآخر كاحتياط
           3. DeterministicProvider دائمًا
      -> citation validation
      -> AiInteraction log
```

### 4.2 متغيرات البيئة المطلوبة

```env
GEMINI_API_KEY=
GEMINI_MODEL=gemini-2.5-flash
OPENAI_API_KEY=
OPENAI_MODEL=gpt-4o-mini
OPENAI_BASE_URL=https://api.openai.com/v1
AI_PROVIDER_ORDER=gemini,openai,deterministic
AI_DAILY_QUOTA=50
```

### 4.3 قواعد القبول

- غياب مفتاح Gemini لا يعطل الدرس إذا كان OpenAI متاحًا.
- غياب مفتاح OpenAI لا يعطل الدرس إذا كان Gemini متاحًا.
- غياب المفتاحين لا يعطل الدرس؛ يرجع deterministic extractive answer من السياق.
- إذا فشل مزود حي بسبب timeout أو quota أو network، يجرب النظام المزود التالي قبل إظهار خطأ.
- لا استدعاء لأي مزود إذا كان grounding غير كافٍ.
- تسجل كل إجابة provider/model/tokens/latency/degraded.

## 5. الخطة التنفيذية النهائية المحدثة

### المرحلة 0 — إصلاحات السلامة والاعتمادية قبل أي ميزة

**الهدف:** ألا نبني واجهات فوق بوابات أو صلاحيات أو محاولات مكسورة.

1. إصلاح `GET /content/textbooks` ليكون **staff-read** لا author-only، حتى يستطيع المعلم فتح رف مواده.
2. إبقاء الكتابة والنشر والتبني خلف بواباتها الحالية؛ المعلم يقرأ فقط.
3. إضافة مفاتيح cache مركزية لـ:
   - `textbookAdministration.outline(textbookKey)`
   - `textbookAdministration.lessonMaterials(lessonKey)`
4. إصلاح فجوة قراءة بيانات متعلم عبر مدرسة أخرى في `learner-access.ts`: staff reads يجب أن تتحقق من مدرسة المتعلم لا من الدور فقط.
5. إضافة الأساس الأول لـ **Local Attempt Recovery**:
   - حفظ draft answers محليًا.
   - تنظيفها عند التسليم.
   - منع حفظ answer keys.
6. تحديث تقرير التدقيق نفسه: إصلاح Markdown، أسماء endpoints، والأرقام القابلة لإعادة العد.
7. إضافة OpenAI adapter خلف `AiProvider` دون تغيير دومين tutoring.
8. تحويل تخصص المعلم إلى علاقة متعددة مع المواد، مع إبقاء حقل النص الحر كـ legacy note.
9. تثبيت query keys لمسار الدرس والمحتوى حتى لا تتسرب بيانات درس سابق إلى درس حالي.

**معايير القبول:**
- المعلم يفتح `/teacher/content` دون 403.
- الطالب لا يستطيع قراءة سطح staff content.
- معلم مدرسة A لا يستطيع قراءة learnerKey في مدرسة B.
- إذا انقطع الاتصال أثناء محاولة، لا تضيع الإجابات المحلية قبل التسليم.
- `AI_PROVIDER_ORDER` يسمح بتشغيل Gemini/OpenAI/deterministic دون تغيير كود الدومين.
- يمكن ربط المعلم بأكثر من مادة منظمة، ولا يعتمد النظام التشغيلي على نص تخصص حر.
- تغيير الدرس في الرابط لا يعرض مواد/اختبارات الدرس السابق من cache قديم.

### المرحلة 1 — تأسيس بنك الأسئلة المصنف + حماية الجفاف

**الهدف:** تفعيل مطلب نوع السؤال ومصدر التمرين قبل بناء الاختبارات والتكليفات عليه، ومنع وصول الطالب إلى pool فارغ.

1. توسيع `QuestionOrigin` بإضافة `MINISTERIAL`.
2. إضافة نموذج مصدر وزاري أو، كحد أدنى مرحلي، توحيد `sourceRef` بصيغة قابلة للبحث.
3. إضافة endpoint لقائمة الأسئلة العامة المفلترة:
   - `GET /content/questions?type=&origin=&status=&gradeKey=&subjectKey=&lessonKey=&conceptKey=&sourceDocumentKey=`
4. تحديث `POST /content/questions` و `PATCH /content/questions/:key` لاستقبال source metadata كاملة.
5. بناء صفحة `/author/questions` كبنك أسئلة فعلي.
6. بناء محرر سؤال ديناميكي حسب `QuestionType`.
7. إضافة فلاتر المصدر: كتاب / معلم / وزاري / AI.
8. تفعيل `QuestionLinkModal` داخل شاشة البنك.
9. إضافة `assessment availability` أو تضمين availability داخل lesson/next-step:
   - عدد الأسئلة المنشورة لكل مفهوم.
   - عدد auto-gradable.
   - هل تكفي CAT؟ هل تكفي fixed practice؟
10. معالجة `assessment.empty_item_pool` في الواجهة كحالة متوقعة لا كخطأ عام.

**معايير القبول:**
- يستطيع المؤلف إنشاء سؤال MCQ/رقمي/نصي/مطابقة/ترتيب/مقالي حسب النوع.
- يستطيع النظام تمييز سؤال كتاب عن سؤال معلم عن سؤال وزاري.
- السؤال الوزاري يحمل سنة/دور/مادة/صف/رقم سؤال أو sourceRef موحد.
- لا ينشر سؤال بلا answer key صالح، إلا المقال مع rubric/مراجعة بشرية واضحة.
- لا ينشر سؤال بلا concept link.
- زر اختبار المفهوم لا يظهر كإجراء قابل للتنفيذ عندما لا توجد أسئلة كافية.
- إذا حصل empty pool رغم ذلك، يرى الطالب بديلًا تربويًا لا صفحة خطأ.

### المرحلة 2 — تمارين المعلم دون تلويث البنك الرسمي

**الهدف:** قبول تمارين المعلم، لكن بملكية ونطاق واضحين.

1. إضافة حق محدود للمعلم لإنشاء `TEACHER` questions، لا تعديل أسئلة الكتاب أو الوزاري.
2. إضافة نطاق ملكية:
   - `authorUserId`
   - `schoolId`
   - `visibility`: `PRIVATE`, `SCHOOL`, `SUBMITTED_FOR_REVIEW`, `GLOBAL`
3. ربط تمارين المعلم بالدروس والمفاهيم مثل أسئلة الكتاب.
4. السماح للمعلم باستخدام أسئلته في تكليف أو اختبار صفي.
5. منع نشرها كبنك رسمي إلا بمراجعة مؤلف/إدارة.
6. إضافة review/promotion workflow لترقية السؤال من `TEACHER` إلى رسمي عند اعتماده.

**معايير القبول:**
- المعلم يرى أسئلته وأسئلة مدرسته وما هو منشور رسميًا.
- المعلم لا يستطيع تعديل سؤال رسمي.
- الطالب لا يرى سؤال المعلم إلا ضمن تكليف/اختبار منشور له أو كتمرين مصرح به.

### المرحلة 3 — إغلاق حلقة الطالب التكيفية + المساعد الذكي داخل الدرس

**الهدف:** تنفيذ قرار `next-step` بدل عرضه فقط، وإعطاء الطالب مساعدة مقيدة بالدرس.

1. تعديل `NextStepCard.onStart`:
   - `LEARN/UNBLOCK` ➜ فتح الدرس/المفهوم المناسب.
   - `REVIEW` ➜ فتح بطاقات المفهوم أو جلسة مراجعة.
   - `PRACTISE/ASSESS` ➜ فتح محاولة ممارسة/تقييم scoped بالمفهوم، بعد availability check.
   - `REMEDIATE` ➜ فتح مورد علاجي + تمرين تثبيت.
2. جعل عناصر `ReviewPage` قابلة للنقر وتفتح deck أو practice للمفهوم المحدد.
3. عدم دمج الواجبات المتأخرة داخل `next-step`; تبقى `due-work` قناة مستقلة.
4. إضافة `TutorDrawer` داخل `LessonPage`:
   - سؤال الطالب.
   - إجابة grounded.
   - citations.
   - refusal state عند نقص السياق.
   - provider/degraded indicator داخلي أو staff-visible لا كتشتيت للطالب.
5. إكمال **Local Attempt Recovery** لمحاولات lesson-check/practice/exam:
   - استعادة draft بعد reload.
   - idempotent answer submit.
   - clear on submit.
6. ضبط `LessonPage` ومسار التعلم:
   - ترتيب الدروس حسب `order`.
   - تمرير `lessonKey`/`conceptKey` الحالي لكل موارد الدرس واختباره.
   - زر العودة للرئيسية بعد الاختبار.
   - زر متابعة الدرس التالي إن وجد.
   - رسالة انتهاء جميع الدروس إذا كان الدرس الأخير.
7. إضافة CTA “استمر من آخر نقطة” في لوحة الطالب/مسار التعلم، مبنيًا على آخر progress/evidence متاح.

**معايير القبول:**
- النقر على توصية REVIEW لا يذهب إلى `/path` العام.
- النقر على PRACTISE/ASSESS يبدأ attempt مناسبًا بالمفهوم فقط إذا كان pool صالحًا.
- النقر على REMEDIATE يعرض موردًا علاجيًا مرتبطًا بالسبب.
- الطالب يستطيع سؤال المساعد من داخل الدرس ويحصل على جواب مع citations أو refusal واضح.
- فشل Gemini لا يكسر واجهة المساعد إذا كان OpenAI أو deterministic متاحًا.
- انتهاء اختبار الدرس لا يترك الطالب عالقًا: يظهر home CTA وnext lesson CTA أو رسالة اكتمال كل الدروس.
- رابط درس معين لا يعرض أسئلة/مواد درس آخر.
- CTA “استمر من آخر نقطة” يفتح آخر نقطة تعلم ذات معنى لا أول درس افتراضيًا.

### المرحلة 4 — واجهة التكليفات ودورة المعلم + التصحيح اليدوي

**الهدف:** تحويل `instruction` من backend كامل بلا واجهة إلى حلقة تدريس، وإغلاق دورة المقال.

1. بناء `/teacher/assignments`:
   - إنشاء خطة.
   - اختيار النشاط: Lesson / Concept / Exam / Review set / Remediation plan.
   - اختيار النطاق: مدرسة + صف + فصل/ترم حالي.
   - نشر/إلغاء.
   - materialise لإلحاق المتأخرين بالتسجيل.
2. بناء بطاقة `Due Work` للطالب من `GET /instruction/due-work` مع فصل `academic` عن `advisory`.
3. بناء `/teacher/interventions` من `GET /remediation/tracker`.
4. ربط التدخلات بخطة علاجية بضغطة واحدة.
5. بناء `/teacher/grading`:
   - طابور إجابات `REQUIRES_MANUAL_REVIEW`.
   - تصحيح وفق rubric.
   - feedback للطالب.
   - اعتماد الدرجة.
6. عند اعتماد التصحيح:
   - تحديث attempt item.
   - إنشاء evidence للمفاهيم.
   - تشغيل mastery recompute.
   - إشعار الطالب بتحديث النتيجة.

**معايير القبول:**
- المعلم ينشر تكليفًا فيرى الطالب العمل المستحق.
- حالة الالتزام تُشتق من evidence لا من زر “تم”.
- المعلم يرى المتأخرين والمتعثرين دون حسابات Frontend.
- تظهر إجابات المقال في طابور التصحيح.
- بعد التصحيح تتحدث نسبة المحاولة والإتقان دون إعادة تسليم من الطالب.

---

### المرحلة 5 — الأسئلة الوزارية والنماذج الامتحانية + الاستيراد الجماعي

**الهدف:** جعل الوزاري مصدرًا تدريبيًا منظمًا لا مجرد شارة، وجعل إدخاله قابلًا للتشغيل على نطاق سنوات ومواد متعددة.

1. إضافة شاشة “النماذج الوزارية” داخل بنك الأسئلة.
2. إدخال/استيراد ورقة وزارية:
   - البلد/الجهة.
   - العام.
   - الصف.
   - المادة.
   - الدور/الجلسة.
   - رقم النموذج أو الرابط.
3. إضافة Import Wizard:
   - لصق Markdown/JSON/CSV.
   - preview.
   - validation.
   - dedupe.
   - bulk save.
4. إضافة أسئلة الورقة إلى البنك مع `origin=MINISTERIAL` و `sourceDocumentId`.
5. ربط كل سؤال بمفهوم ودرس، فرديًا أو جماعيًا.
6. إنشاء اختبارات تدريب وزارية من هذه الأسئلة.
7. تقارير تغطية:
   - أي مفاهيم تظهر كثيرًا في الوزاري؟
   - أي مفاهيم لا تغطيها أسئلة كافية؟
   - ما توزيع أنواع الأسئلة في الورقة الوزارية؟

**معايير القبول:**
- يستطيع المستخدم فلترة البنك إلى “وزاري فقط”.
- يستطيع إنشاء تدريب “نمط وزاري” من مصدر موثق.
- يمكن إدخال ورقة كاملة دون إدخال سؤال سؤال يدويًا.
- لا يغير كون السؤال وزاريًا قواعد mastery؛ هو provenance واختيار ممارسة فقط.

---

### المرحلة 6 — التشخيص القبلي وتحديد المستوى

**الهدف:** ألا يبدأ الطالب من الدرس الأول افتراضيًا إذا كانت evidence التشخيصية تقول غير ذلك.

1. بناء تجربة Diagnostic عند بداية مادة/عام/كتاب.
2. اختيار concepts محورية من prerequisites وبدايات الوحدات.
3. استخدام `AttemptKind.DIAGNOSTIC` بسياسة وزن واضحة.
4. بعد التشخيص:
   - ضبط توصيات next-step.
   - اقتراح مسار تأسيسي عند الضعف.
   - فتح/تخطي مراجعات عند وجود إتقان مثبت.
5. شاشة معلم cohort diagnostic:
   - توزيع الطلاب حسب الاستعداد.
   - مفاهيم تحتاج مراجعة جماعية.

**معايير القبول:**
- الطالب الجديد يرى تشخيصًا قبليًا مناسبًا بدلاً من بداية عمياء.
- التشخيص يؤثر على التوصية/الانطلاق دون تجاوز غير مبرر لقفل المنهج.
- المعلم يرى فجوات الفصل قبل بدء الوحدة.

---

### المرحلة 7 — التأليف والاستيراد وجودة المحتوى

**ملاحظة تنفيذية:** هذه المرحلة لا تُقاس فقط بوجود CRUD، بل بقدرة المؤلف/الإدارة على معرفة هل الكتاب جاهز لتجربة طالب سليمة، ثم الانتقال مباشرة إلى الإجراء الصحيح.

1. تحسين إدارة الكتب:
   - مؤشرات تشغيلية أعلى الصفحة.
   - روابط مباشرة لإدارة محتوى كل كتاب.
   - مسح مرشحات سريع، ودورة نشر/تبنّي واضحة.
2. تحسين إدارة المحتوى:
   - عرض هرمي للوحدة/الدرس بدل جدول مسطح فقط.
   - Drawer مواد الدرس.
   - معاينة درس وربط أسئلة ومراجعة جاهزية من نفس السياق.
3. بناء واجهة تأليف الوحدات/الدروس/المفاهيم.
4. دمج استيراد Excel/PDF/وزاري بعد تثبيت نموذج السؤال ومصدره، مع preview/validation/dedupe قبل الحفظ الجماعي.
5. توسيع `readiness` ليشمل:
   - درس بلا موارد أو بلا قراءة نشطة.
   - مفهوم بلا أسئلة منشورة.
   - مفهوم بلا أسئلة auto-gradable صالحة للتدريب/CAT.
   - مفهوم بلا flashcards أو موارد علاجية كبديل تربوي.
   - أسئلة بلا concept links.
   - مفاهيم لا تملك الحد الأدنى لـ CAT.
   - مفاهيم لا تملك بديل fixed-practice.
6. عرض readiness داخل سياق إدارة المحتوى لا كشاشة منفصلة بعيدة عن الوحدة/الدرس.
7. جدولة projector لإحصاءات صحة الأسئلة بدل refresh يدوي فقط.
8. عرض لوحة `item-health` حسب النوع والمصدر: كتاب / معلم / وزاري / AI.

---

### المرحلة 8 — قرار الشعب وتعيين المعلم المشروط

لا ننفذ `ClassSection/TeacherAssignment` كمرحلة إلزامية الآن. ننفذه فقط إذا تحقق واحد من هذه الشروط:

1. المدرسة الواحدة لديها شعب فعلية أ/ب/ج.
2. أكثر من معلم يدرّس نفس المادة لنفس الصف في نفس المدرسة.
3. مطلوب تكليف واجب لشعبة لا تساوي كامل الصف.
4. مطلوب تقرير أداء خاص بمعلم/مادة لا يمكن اشتقاقه من Enrollment وحده.

إذا لم يتحقق أي شرط، فالبديل المعتمد هو:

1. **teacher multi-subject** عبر علاقة مواد منظمة للمعلم.
2. تقارير teacher/subject مشتقة من `Enrollment` + المادة + الكتاب المعتمد، لا من جدول شعبة مستقل.
3. التكليفات تستهدف grade/school/enrollment scope كاملًا، مع عدم ادعاء وجود شعبة ليست موجودة في النموذج.
4. يبقى `ClassSection/TeacherAssignment` قرارًا منتجيًا مؤجلًا، لا دينًا تقنيًا مفتوحًا.

إذا تحقق الشرط لاحقًا، النموذج المقترح:

```prisma
model ClassSection {
  schoolId       String
  gradeId        String
  academicYearId String
  termId         String?
  name           String
}

model TeacherAssignment {
  teacherUserId  String
  sectionId      String
  subjectId      String
}
```

### المرحلة 9 — البيت، الإشعارات، وترحيل العام

1. بوابة ولي الأمر:
   - تقدم الأبناء.
   - الواجبات المستحقة.
   - إنشاء مهام advisory فقط.
   - إرشادات دعم لا تتحول إلى تحكم أكاديمي.
2. بطاقة طالب منفصلة:
   - “توصيات ولي الأمر”.
   - لا تختلط مع Due Work الأكاديمي.
3. Inbox/Notifications:
   - متأخرات أكاديمية.
   - تدخلات مفتوحة.
   - مراجعة أسئلة تحتاج تدقيق.
   - نتائج مقالية تم تصحيحها.
   - توصيات ولي الأمر كإشعار advisory.
4. ترحيل عام دراسي:
   - إغلاق العام.
   - نسخ أو ترقية التسجيلات.
   - اعتماد كتب العام الجديد.
   - قرار إعادة تشغيل diagnostics للعام الجديد.

## 6. ترتيب الأولوية النهائي المختصر

1. **P0 — سلامة واعتمادية:** رف المعلم 403 + staff cross-school read + query keys + أساس local recovery + OpenAI adapter + تصحيح الوثيقة.
2. **P0/P1 — تخصصات المعلمين متعددة المواد:** علاقة منظمة مع `Subject` تدعم أكثر من مادة ولا تعتمد على نص حر.
3. **P1 — بنك الأسئلة المصنف:** نوع السؤال + مصدر السؤال + `MINISTERIAL` + قائمة/فلاتر/محرر ديناميكي + concept links.
4. **P1 — Empty Pool Guard:** availability/preflight + fallback تربوي + معالجة UX لـ `assessment.empty_item_pool`.
5. **P1 — تمارين المعلم scoped:** تمارين خاصة/مدرسية دون تعديل البنك الرسمي.
6. **P2 — إغلاق Next-Step UI ومسار الدرس:** زر التوصية ينفذ النشاط الحقيقي، والدروس لا تختلط، وبعد الاختبار تظهر home/next/final CTAs.
7. **P2 — استمر من آخر نقطة:** CTA مبني على آخر progress/evidence للتعلم.
8. **P2 — In-Lesson AI Tutor:** Drawer داخل الدرس + Gemini/OpenAI/deterministic + citations/quota/refusal.
9. **P2 — Local Attempt Recovery الكامل:** IndexedDB + idempotent submit + restore.
10. **P2 — التكليفات والتدخلات:** واجهة المعلم + Due Work الطالب + Remediation radar.
11. **P2 — Manual Grading Queue:** تصحيح مقالي + feedback + evidence/recompute.
12. **P3 — الوزاري كنماذج امتحانية:** source documents + bulk ingestion + تدريبات وزارية + تقارير تغطية.
13. **P3 — Diagnostic Placement:** بداية عام/مادة مبنية على attempt تشخيصي.
14. **P4 — إدارة الكتب والمحتوى:** مؤشرات، فلاتر، روابط عمل، عرض هرمي، readiness موسع.
15. **P4 — التأليف والاستيراد:** content authoring + Excel/PDF import.
16. **P4 — جودة الأسئلة:** scheduled item-health + dashboards by type/source/provider.
17. **P5 — Parent portal والإشعارات وترحيل العام.**
18. **Conditional — الشعب وتعيين المعلم:** فقط عند تحقق triggers المنتجية.

## 7. لماذا لا تُقبل بعض الاقتراحات بصيغتها الحالية؟

| الاقتراح | القرار | سبب عدم القبول بصيغته الحالية | الصيغة المقبولة |
|---|---|---|---|
| إضافة `ClassSection/TeacherAssignment` فورًا | غير مقبول كأولوية فورية | يصطدم بقرار موثق أن الفصل Query، وسيخلق مصدر حقيقة ثانيًا قبل وجود مطلب منتجي ثابت. | تنفيذه كـ trigger عند وجود شعب أو تعدد معلمين لنفس الصف/المادة. |
| اعتبار “وزاري” نوع سؤال | غير مقبول | الوزاري ليس نوع تصحيح؛ قد يكون MCQ أو مقاليًا أو رقميًا. | `QuestionType` للتصحيح، و`QuestionOrigin=MINISTERIAL` للمصدر. |
| وضع الوزاري داخل `TextbookQuestionRole` | غير مقبول | `TextbookQuestionRole` خاص بما طُبع في الكتاب فقط. | مصدر مستقل أو `QuestionSourceDocument`. |
| السماح للمعلم بتعديل بنك الأسئلة الرسمي | غير مقبول | يخرق ملكية المحتوى وقفل الكتاب بعد النشر. | تمارين معلم scoped للمعلم/المدرسة، ثم review/promotion إن أريد. |
| جعل مصدر السؤال يغير mastery أو adaptive selection تلقائيًا | غير مقبول | provenance وصفي؛ mastery يجب أن ينتج من evidence فقط لا من مصدر السؤال. | استخدام المصدر كفلتر ممارسة/اختبار صريح ومسجل في attempt policy. |
| دمج الواجبات المتأخرة في `next-step` | غير مقبول | `next-step` قرار تربوي مبني على mastery، والواجبات قناة إدارية مستقلة. | بطاقة Due Work منفصلة بجانب Next Step. |
| جعل ولي الأمر يضع واجبات أكاديمية ملزمة | غير مقبول الآن | قد يخلط authority الأكاديمي ويؤثر على التقارير. | Parent tasks advisory فقط ولا تدخل في completion الأكاديمي. |
| إضافة إعدادات نظام عامة فوق `SystemSetting` الآن | غير مقبول | جدول بلا runtime consumers؛ بناء UI له يصنع إعدادات ميتة. | إضافة إعداد محدد فقط عندما يقرأه دومين فعليًا. |
| إضافة أنواع أسئلة كنص حر | غير مقبول | يكسر evaluator وpublish gate. | enum exhaustively handled في schema/domain/frontend. |
| عرض لوحة صدارة عامة للطلاب | غير مقبول | خطر خصوصية وتسريب بين المدارس. | لوحة صدارة staff-only أو cohort/school scoped بضوابط. |
| تشغيل CAT حتى عند نقص الأسئلة | غير مقبول | يعطي تجربة مكسورة أو نتيجة ذات ثقة كاذبة. | availability + fallback مصرح وموسوم. |
| استخدام AI لتصحيح المقال تلقائيًا نهائيًا | غير مقبول للنسخة الأولى | خطر تربوي وعدالة وشفافية. | AI-assisted suggestion فقط، واعتماد بشري صريح. |
| جعل المساعد الذكي عامًا بلا Grounding | غير مقبول | خطر هلوسة وخروج عن المنهج. | In-lesson grounded tutor مع citations/refusal/quota. |
| إدخال الوزاري سؤالًا بسؤال فقط | غير مقبول تشغيليًا | ورقة واحدة قد تحتوي عشرات الأسئلة، والسنوات المتعددة تجعل الإدخال اليدوي مستحيلًا. | Bulk importer مع preview/validation/dedupe. |
| حفظ محاولات الطالب في الذاكرة فقط | غير مقبول في البيئة المستهدفة | انقطاع الاتصال سيضيع إجابات الطالب. | IndexedDB/local recovery + idempotent submit. |

## 8. القرار النهائي

الخطة النهائية بعد التحديث تصبح:

- **أكثر صرامة معماريًا** في بنك الأسئلة.
- **أكثر أمانًا** لأنها تبدأ بإصلاحات صلاحية وسلامة.
- **أكثر واقعية تشغيليًا** لأنها تضيف bulk ingestion للوزاري.
- **أكثر اكتمالًا تربويًا** لأنها تغلق: CAT fallback، المقال، التشخيص القبلي، المساعد الذكي، ومهام ولي الأمر الاستشارية.
- **أكثر مرونة تقنيًا** لأنها تضيف OpenAI بجانب Gemini خلف `AiProvider` واحد مع deterministic fallback.
- **أدق تشغيليًا** لأنها تجعل تخصصات المعلمين علاقات مواد متعددة بدل نصوص حرة.
- **أوضح للطالب** لأنها تضبط استكمال الدروس، العودة للرئيسية، متابعة الدرس التالي، والاستمرار من آخر نقطة.
- **أقوى للإدارة** لأنها ترفع إدارة الكتب والمحتوى من جداول فقيرة إلى واجهات تشغيلية ذات مؤشرات ونوايا عمل.

القاعدة الحاكمة التي لا تتغير:

> **QuestionType للتصحيح، QuestionOrigin للمصدر، QuestionConcept للإتقان، AttemptPolicy للاختيار.**
