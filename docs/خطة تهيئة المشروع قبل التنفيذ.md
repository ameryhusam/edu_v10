# خطة تهيئة المشروع والتدقيق النهائي قبل تنفيذ الخطة النهائية

> هذه الوثيقة مكملة وملزمة للخطة `docs/الخطة النهائية للمشروع.md`. لا يبدأ تنفيذ Workspace أو Edu7 Content Engine قبل إكمال مراحل التهيئة والتدقيق هنا. الهدف هو إزالة التعارضات الموجودة حالياً في Backend وFrontend، ثم تنفيذ خطة المحتوى فوق أساس قابل للتشغيل والاختبار.

## 1. قاعدة التنفيذ

نفّذ المراحل بالترتيب، ولا تنتقل إلى مرحلة لاحقة إذا فشل أحد شروط القبول في المرحلة الحالية.

المسار المعتمد:

```text
تهيئة المستودع والتدقيق
  -> إصلاح عقد الحالات والرؤية
  -> إصلاح إدارة الكتب والمحتوى
  -> تثبيت API والـ query contracts
  -> إضافة الأصول والتخزين
  -> Workspace/Content Engine
  -> import/dry-run/apply
  -> عرض PDF والصور والكاش
  -> إصلاح Learning Path
  -> AI enrichment من DB
  -> اختبارات end-to-end
```

ممنوع أثناء التنفيذ:

- إنشاء مسار كتابة جديد يتجاوز `ContentImportService`.
- جعل Frontend يقرر معنى `DRAFT` أو `PUBLISHED` بدلاً من Backend.
- جعل الطالب يرى محتوى غير منشور.
- اعتبار اعتماد الكتاب خارج Edu7 جزءاً من دورة النشر الداخلية.
- استخدام `orderIndex` كهوية.
- حذف المحتوى القديم عند غيابه من تحديث جديد.
- تخزين PDF أو الصور داخل JSON/Base64.

الحقائق التي يجب الحفاظ عليها:

- `ContentImportService` يستقبل package parsed، وليس filesystem أو PDF.
- الهيكل يكتب من خلال `ContentAuthoringService`.
- الأسئلة تكتب من خلال `ItemBankService`.
- الاستيراد الجاف افتراضي.
- مفاتيح textbook/unit/lesson/concept مشتقة من identifiers المشتركة.
- `Question` يمكن أن يكون موضوعاً في lesson بدون concept، لكن لا يدخل المسار التشخيصي أو adaptive pool حتى يرتبط بمفهوم.
- المحتوى learner-facing يمر عبر predicates النشر في `published-content.ts`، وليس عبر Frontend filter فقط.

- يوجد `importPackage` في API client، ويوجد `ContentImportModal`، لكن modal الحالي يدعم CSV/JSON/Text outline ولا يمثل بعد Workspace ZIP و`index.json` وasset inventory وdry-run الكامل.
- شاشات إدارة الكتب تحسب `publishedCount` و`draftCount`، لكن يجب التأكد أن مصدر البيانات لا يطلب `status: PUBLISHED` في طبقة الصفحة أو hook، وأن DRAFT يصل إلى الإدارة فعلياً.
- `ExamManagementPanel` يطلب textbooks بحالة `PUBLISHED` وهذا صحيح للأسئلة/الامتحانات learner-facing أو المرتبطة ببنك منشور، لكنه لا يجوز نسخه إلى إدارة الكتب والمحتوى الداخلية.
- `grade-materials-view.tsx` يعرض زر نشر، بينما السياسة المطلوبة هنا هي أن الكتاب الخارجي يدخل Edu7 كمصدر جاهز، وحالة الكتاب داخل Edu7 تعكس جاهزية محتوى Edu7 فقط. لذلك يجب تسمية الإجراء بوضوح: إرسال محتوى Edu7 للمراجعة/نشره، وليس اعتماد الكتاب الخارجي.
- توجد مسارات ومكونات متعددة للمودالات؛ لا تضف modal جديداً إذا كان يمكن تطوير `ContentImportModal` أو `TextbookOutlineModal` دون خرق حدود التصميم.
- `LessonPage` يعرض resources الحالية، لكنه يحتاج asset metadata وPDF/image viewer وcache states.
- `junior-dashboard` وreview يستخدمان قرارات Backend جزئياً، ويجب منع أي إعادة حساب frontend لـ next-step أو mastery.

## 4. المرحلة 1: إصلاح نموذج رؤية الكتب والحالات

### المشكلة

الكتب المسودة يجب أن تظهر في إدارة الكتب وإدارة المحتوى، لكن لا تظهر للطالب. بعض الشاشات قد تستخدم published-only query في مكان إداري، أو تقصي DRAFT داخل filtering محلي.

### Backend

#### تعديل

```text
src/interface/http/content.routes.ts
src/contexts/content/application/textbook-administration.service.ts
src/infrastructure/database/textbook-administration.repository.ts
```

#### التعليمات

1. اجعل list textbooks الإداري يقبل:

```text
status = DRAFT | IN_REVIEW | PUBLISHED | ARCHIVED
status غير موجود = كل الحالات المسموح بها للدور الإداري
```

2. لا تضع `PUBLISHED` كـ default في repository الإداري.
3. اجعل learner-facing readers تستخدم predicates موحدة من:

```text
src/infrastructure/database/published-content.ts
```

وتشترط:

```text
textbook PUBLISHED
unit active
lesson active
concept active
```

4. لا تخلط `TextbookAdoption` مع publication status:

```text
publication = هل محتوى Edu7 جاهز للمتعلم؟
adoption = هل المدرسة تستخدم الكتاب؟
```

5. لا تجعل `ensure-for-grade` أو adoption يخفي DRAFT من الإدارة.
6. لا تستخدم `status` في Frontend لإخفاء الكتاب الإداري؛ server query يحدد scope، والواجهة تعرض كل الحالات التي طلبتها.

### Frontend

#### تعديل

```text
web/src/features/content/content.api.ts
web/src/pages/admin/textbooks-admin.tsx
web/src/features/content/grades-active-view.tsx
web/src/features/content/grade-materials-view.tsx
web/src/shared/api/query-keys.ts
```

#### التعليمات

1. استدعاء الإدارة بدون `status: 'PUBLISHED'`.
2. أضف filter صريحاً:

```text
All / DRAFT / IN_REVIEW / PUBLISHED / ARCHIVED
```

3. اعرض counters صحيحة لكل الحالات.
4. لا تجعل `gradeMaterials` مبنياً على published فقط.
5. احتفظ بـ published-only query في شاشات learner أو exam creation حيث يلزم.
6. أظهر `PublicationBadge` وشرح الحالة.
7. لا تسمِّ زر `APPROVE` اعتماد الكتاب الخارجي؛ استخدم نصاً يوضح أنه نشر محتوى Edu7 بعد المراجعة.
8. عند عدم وجود كتب DRAFT، فرّق بين:
   - لا توجد كتب.
   - filter الحالي يستبعدها.
   - query failed.

### شروط القبول

- يظهر DRAFT وIN_REVIEW وPUBLISHED وARCHIVED في إدارة الكتب عند اختيار All.
- لا يظهر DRAFT في learner textbooks أو learning path أو lesson view.
- لا يظهر محتوى DRAFT في `findPoolByConcepts` أو exam catalog.
- تغيير status يحدث من Backend transition وليس patch مباشر.

## 5. المرحلة 2: إصلاح مفهوم النشر داخل Edu7

### القرار

Edu7 لا يعتمد صلاحية الكتاب الخارجي. هو يستقبل المصدر ويجهز محتواه. `PublicationStatus` يعبر فقط عن جاهزية محتوى Edu7 المستخرج/المضاف والمراجع.

### Backend

#### تعديل

```text
src/contexts/content/application/publishing.service.ts
src/interface/http/content.routes.ts
src/infrastructure/database/published-content.ts
```

#### التعليمات

1. أبقِ transition lifecycle الحالي، لكن وثّق semantics الجديدة في code comments وerror messages.
2. `SUBMIT` يعني إرسال محتوى Edu7 للمراجعة.
3. `APPROVE` يعني جعل محتوى Edu7 learner-visible بعد تحقق readiness.
4. لا تسمح `APPROVE` إذا كانت assets المطلوبة أو resources أو concepts أو question pool غير جاهزة.
5. لا تجعل import package يكتب `PUBLISHED` حتى لو كان المصدر معلناً جاهزاً.
6. لا تغير learner queries لتعرض DRAFT من أجل الإدارة.
7. افصل readiness عن external approval:

```text
external source metadata = provenance
Edu7 readiness = content completeness
Edu7 publication = learner visibility
```

### Frontend

#### تعديل

```text
web/src/features/content/textbook-accredit-modal.tsx
web/src/features/content/grade-materials-view.tsx
web/src/features/content/textbook-outline-modal.tsx
```

#### التعليمات

- غيّر labels والشرح لتوضيح الفرق.
- اجعل `TextbookAccreditModal` خاصاً بـ adoption/school use، لا publishing.
- اجعل publish action داخل إدارة المحتوى، لا adoption modal.
- اعرض readiness report قبل submit/approve.
- لا تعرض publish action للـ learner.

### شروط القبول

- يمكن للإدارة فتح DRAFT ومراجعة outline/assets/readiness.
- الطالب لا يرى إلا PUBLISHED.
- adoption لا يحول الكتاب إلى PUBLISHED.
- external PDF provenance لا يتجاوز approval lifecycle.

## 18. معايير القبول النهائية

لا تعتبر الخطة منفذة حتى تتحقق الشروط التالية:

### إدارة الكتب

- DRAFT يظهر في الإدارة.
- IN_REVIEW وPUBLISHED وARCHIVED تظهر حسب filter.
- الإدارة ترى محتوى DRAFT وموارده لمراجعته.
- الطالب لا يرى DRAFT أو ARCHIVED.
- adoption لا يساوي publication.

### Engine/Workspace

- `index.json` هو entry point.
- كل unit/lesson JSON وPDF يحمل الرقم.
- resources directory داخل كل درس.
- الصور/PDF خارج JSON.
- prerequisites وmisconceptions وresources وflashcards وpages/chunks لا تسقط.
- canonical question export يستخدم `answerKey.correctChoiceIds`.
- benchmark يعمل فعلياً.

### Backend

- كل import يبدأ dry-run.
- كل write يمر عبر canonical services.
- asset metadata وchecksum محفوظة.
- no silent deletion.
- unchanged/conflict واضحان.
- AI content DRAFT.
- grounding قابل للاسترجاع.

### Frontend/Web/Android

- import UI مكتمل.
- PDF الدرس يعرض عند الطلب.
- الصور والملخصات تعرض عند الطلب.
- cache يعمل ويستخدم version/hash.
- المسار يعرض قرار Backend الصحيح.
- الأخطاء والمودالات responsive وaccessible.
- Android يستخدم نفس asset API.

### الجودة

- `npm run verify` ناجح.
- Web typecheck/architecture/tests ناجحة.
